===============================================================================
      EXPLANATION: Forgot Password Returns New Password in API Response
===============================================================================

Bug #3 from the Bug Audit Report
File Involved (Backend):  UserController.java — Lines 205 to 231
File Involved (Frontend): Login.jsx — Lines 79 to 87


───────────────────────────────────────────────────────────────────────────────
  WHAT SHOULD HAPPEN (THE EXPECTED BEHAVIOR)
───────────────────────────────────────────────────────────────────────────────

When a user forgets their password and requests a reset, most websites
follow this process:

  1. The user enters their email address and clicks "Forgot Password."
  2. The system generates a new temporary password (or a reset link).
  3. The system sends that password (or link) to the user's EMAIL.
  4. The user checks their email, gets the new password, and uses it to
     log in.

The key point is: the new password should ONLY be delivered through
the user's email, which is a private channel. It should NEVER be shown
directly on the website or sent back as part of the server's response.


───────────────────────────────────────────────────────────────────────────────
  WHAT ACTUALLY HAPPENS (THE BUG)
───────────────────────────────────────────────────────────────────────────────

In the Duyanan Restaurant system, the forgot password feature is broken
in TWO ways:

  1. NO EMAIL IS SENT
     Even though the project has email settings configured (Gmail SMTP
     in the settings file), the code NEVER actually sends an email.
     There is simply no email-sending logic written in the forgot
     password function. The email settings just sit there unused.

  2. THE NEW PASSWORD IS SENT BACK IN THE SERVER'S REPLY
     Instead of emailing the password, the system includes the new
     plaintext password directly in the data it sends back to the
     website. Think of it like this: instead of mailing you a private
     letter with your new key, the locksmith holds up a sign with your
     new key written on it for everyone nearby to see.

To make things worse, the FRONTEND (the part the user sees) shows a
popup that says:

     "Check Your Email!"

This is MISLEADING because no email was ever sent. The user will wait
for an email that never arrives, and they will never receive their new
password.


───────────────────────────────────────────────────────────────────────────────
  WHY IS THIS A PROBLEM?
───────────────────────────────────────────────────────────────────────────────

This bug creates two serious issues:

  A. SECURITY RISK — Password Exposure

     When the new password is included in the server's response, it
     travels over the network in readable form. This means:

       - Anyone monitoring the network (for example, on public Wi-Fi)
         could potentially intercept and read the new password.
       - The password could be stored in browser history, server logs,
         or network logs where others might find it.
       - Developers or anyone with access to browser developer tools
         can see the password in plain text.

     In short, the password is being handled in an unsafe way.

  B. USER EXPERIENCE PROBLEM — The Feature Simply Doesn't Work

     From the user's perspective, the forgot password feature is
     completely broken:

       - They click "Forgot Password" and enter their email.
       - They see a message saying "Check Your Email!"
       - They check their email... but nothing ever arrives.
       - Meanwhile, their old password has ALREADY been replaced with
         a new one they never received.
       - They are now locked out of their account with no way to get
         back in (unless they contact support or try the forgot
         password process again — which will just repeat the same
         broken cycle).


───────────────────────────────────────────────────────────────────────────────
  WHERE EXACTLY IS THE PROBLEM IN THE CODE?
───────────────────────────────────────────────────────────────────────────────

  BACKEND (UserController.java, Lines 227–230):

     The function that handles the forgot password request generates a
     new password and saves it to the database — that part is fine.
     But then, instead of sending an email, it puts the new password
     directly into the response it sends back:

        "newPassword", newPassword   <-- This is the problem line

     This line sends the actual password back as data in the response.

  FRONTEND (Login.jsx, Lines 79–87):

     The website receives the response (which contains the new
     password), but it doesn't even show it to the user. Instead,
     it just displays "Check Your Email!" — which is false.

     So the password is exposed in an insecure way in the background
     (visible in developer tools or network logs) but is never
     actually shown or delivered to the user in any usable way.


───────────────────────────────────────────────────────────────────────────────
  HOW SHOULD IT BE FIXED?
───────────────────────────────────────────────────────────────────────────────

There are two recommended approaches:

  OPTION A — Actually send the email (Recommended)

     - Write the code to send an email using the email settings that
       already exist in the project.
     - Include the new password (or better yet, a password reset link)
       in the email body.
     - Remove "newPassword" from the server's response so it is no
       longer exposed.
     - Keep the "Check Your Email!" message on the frontend since an
       email will now actually be sent.

  OPTION B — Show the password on screen (Quick fix, less secure)

     If email sending is not possible for now:

     - Remove "newPassword" from the server's response (don't send it
       over the network).
     - Generate the password and show it directly on the screen via a
       popup, making it clear to the user: "Here is your new temporary
       password. Please save it and change it after logging in."
     - Change the misleading "Check Your Email!" message to something
       accurate.

     Note: Option B is less secure than Option A, but it is honest and
     functional, which is better than the current broken behavior.


───────────────────────────────────────────────────────────────────────────────
  IN SIMPLE TERMS
───────────────────────────────────────────────────────────────────────────────

Imagine you lost the key to your locker. You ask the front desk for a
new key. They say, "We've mailed a new key to your home!" But they
never actually mailed it. Instead, they wrote the key code on a sticky
note and left it on the counter where anyone could read it — but you
already walked away expecting a letter, so you never saw the sticky
note either.

That is essentially what this bug does. The system promises to email
the new password, never sends the email, and leaves the password
exposed in a place the user won't look but others might find.


===============================================================================
          STEPS TO REPRODUCE (How to See the Bug Yourself)
===============================================================================

Before you begin, make sure both servers are running:
  - Backend  → run "./mvnw.cmd spring-boot:run" inside the backend folder
  - Frontend → run "npm run dev" inside the frontend folder

You need a registered account to test this. If you don't have one yet,
go to http://localhost:5173, click Register, and create an account with
any email and password. Remember the email you used.


───────────────────────────────────────────────────────────────────────────────
  METHOD 1: Through the Website (See the Misleading Message)
───────────────────────────────────────────────────────────────────────────────

  Step 1 — Open the Login Page
     Open your browser and go to: http://localhost:5173/login
     (Or click "Login" from the website's navigation bar.)

  Step 2 — Click "Forgot Password?"
     On the login page, look for the "Forgot Password?" link and click
     it. A popup will appear asking for your email address.

  Step 3 — Enter Your Email
     Type the email address of your registered account into the popup
     and click "Submit" (or the confirm button).

  Step 4 — Observe the Misleading Message
     You should see a SUCCESS popup that says:

        ✅ "Check Your Email!"

     But here's the problem: NO email was actually sent. If you go check
     your inbox, there will be nothing there.

  Step 5 — Try to Log In with Your OLD Password
     Go back to the login form and try logging in with your old password.
     It will FAIL because the system already replaced your password with
     a new random one that you never received.

     ➤ You are now LOCKED OUT of your account.

  WHAT THIS PROVES:
     The forgot password feature tells you to check your email, but
     never sends one. Your old password is gone, and you have no way
     to know your new password. The feature is completely broken from
     the user's perspective.


───────────────────────────────────────────────────────────────────────────────
  METHOD 2: Using Browser Developer Tools (See the Exposed Password)
───────────────────────────────────────────────────────────────────────────────

  This method lets you see the SECURITY side of the bug — the new
  password being sent back in the server's response where it shouldn't be.

  Step 1 — Open Developer Tools
     In your browser (Chrome, Edge, or Firefox), press F12 on your
     keyboard. This opens the Developer Tools panel.

  Step 2 — Go to the Network Tab
     In the Developer Tools panel, click on the tab that says "Network"
     at the top. This shows all the data being sent between your browser
     and the server.

  Step 3 — Open the Login Page
     Go to: http://localhost:5173/login

  Step 4 — Click "Forgot Password?" and Enter Your Email
     Same as Method 1: click "Forgot Password?", enter your email, and
     submit.

  Step 5 — Find the Request in the Network Tab
     In the Network tab, look for an entry called "forgot-password".
     Click on it.

  Step 6 — View the Response
     Click on the "Response" sub-tab (or "Preview"). You will see
     something like this:

        {
           "message": "Your new password has been generated.",
           "newPassword": "xK7#mNp2Qr"
        }

     ⚠️ There it is! The new password is sitting right there in plain
     text in the server's response. Anyone who knows how to open
     Developer Tools (or anyone monitoring network traffic) can see it.

  WHAT THIS PROVES:
     The new password is being sent back as part of the server's reply.
     This is a security risk because:
       - It's visible in browser Developer Tools
       - It could be logged in server/proxy logs
       - It could be intercepted on unsecured networks
     A password should NEVER be sent this way. It should only be
     delivered through a secure, private channel like email.


───────────────────────────────────────────────────────────────────────────────
  METHOD 3: Using the API Directly (For a Clearer View)
───────────────────────────────────────────────────────────────────────────────

  If you want to see the bug in its simplest form without using the
  website at all, you can talk directly to the server.

  Step 1 — Open a Terminal or Command Prompt

  Step 2 — Run This Command (replace with your registered email):

     curl -X POST http://localhost:8080/api/auth/forgot-password ^
          -H "Content-Type: application/json" ^
          -d "{\"email\": \"your_email@example.com\"}"

     (On Mac/Linux, use backslash \ instead of ^ for line breaks.)

  Step 3 — Read the Response
     The server will reply with something like:

        {
           "message": "Your new password has been generated.",
           "newPassword": "Ab3$kWz9Nf"
        }

     The password is right there in the response. No email was sent.

  WHAT THIS PROVES:
     Even without a website, anyone who knows the API address can
     request a password reset for ANY email, and the server will hand
     back the new password directly. This is a serious security flaw.
