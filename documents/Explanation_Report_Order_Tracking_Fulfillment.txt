================================================================================
           EXPLANATION REPORT: ORDER TRACKING & FULFILLMENT DASHBOARD
================================================================================

This document provides a simple, easy-to-understand breakdown of the test results 
for the Order Tracking & Fulfillment Dashboard. It details why test case 
TC-STS-032 failed, explains the defect found, outlines the test coverage and 
identified risks, and provides clear recommendations to fix the issues.

--------------------------------------------------------------------------------
1. WHY TEST CASE TC-STS-032 FAILED
--------------------------------------------------------------------------------
* What the Test Case Was Checking:
  We wanted to ensure that if the frontend tries to update an order that does 
  not exist in the database (for example, Order ID 999999), the system:
  1. Rejects the request with an "HTTP 404 Not Found" error.
  2. Nicely displays an error popup (modal) to the user using the SweetAlert2 library.

* What Actually Happened (Why it Failed):
  - The backend server behaved correctly by returning a "404 Not Found" error.
  - However, the backend sent this error message as PLAIN TEXT ("Not Found").
  - The frontend website was written to assume that the backend ALWAYS replies in 
    JSON format (a structured data format).
  - When the frontend website received the plain text "Not Found" response, it 
    tried to read it as JSON anyway.
  - This caused a JavaScript crash in the browser console (SyntaxError: Unexpected 
    token 'N').
  - Because of this crash, the website script stopped running immediately, which 
    blocked the SweetAlert2 error popup from showing up. The page just froze 
    without letting the user know what went wrong.

--------------------------------------------------------------------------------
2. EXPLANATION OF THE "DEFECTS FOUND" SECTION (DEF-STS-001)
================================================================================
* Defect ID: DEF-STS-001
* Summary: Frontend crashes when trying to read non-JSON 404 error responses.

* Simple Breakdown of the Bug:
  - This bug is a mismatch in communication between the backend (server) and the 
    frontend (user interface).
  - The backend speaks "Plain Text" when returning error pages, but the frontend 
    only understands "JSON" when it receives responses. 
  - When the frontend calls "res.json()" on a plain-text response, the web page 
    breaks.
  - Additionally, the frontend does not check if the server request succeeded 
    (no "!res.ok" check) for status updates, meaning it has no fallback plan if 
    the network or database fails.

--------------------------------------------------------------------------------
3. EXPLANATION OF THE "TEST COVERAGE" SECTION
================================================================================
The test coverage report tracks which features (requirements) were tested and 
whether they passed or failed:

* REQ-FDF-030 to REQ-FDF-032 (PASSED):
  - Testing covered: Loading active orders, sorting them from newest to oldest, 
    and displaying a clean "No active orders" message when the database is empty.
  - Everything here works perfectly.

* REQ-FDF-040 to REQ-FDF-042 (FAILED):
  - Testing covered: Changing order status (e.g., Pending to Preparing), handling 
    updates for non-existent orders, and ensuring total prices/delivery fees 
    don't change during status updates.
  - Status: FAILED. Even though changing status and prices work, the failure to 
    handle non-existent orders (TC-STS-032) means this entire requirement block 
    cannot be marked as passed.

* REQ-FDF-050 to REQ-FDF-052 (PASSED):
  - Testing covered: Requiring a cancellation reason when canceling orders, 
    preventing users from typing only spaces, and saving the reason in the database.
  - Everything here works perfectly.

--------------------------------------------------------------------------------
4. EXPLANATION OF THE "RISKS IDENTIFIED" SECTION
================================================================================
Risks represent potential problems that could cause issues in the real world 
if they aren't fixed:

* Risk 1: Uncaught Front-End Exceptions on Non-JSON Errors
  - Plain English: If the server goes down, loses database connection, or returns 
    any error page that isn't JSON formatted, the entire web page crashes.
  - What it means to users: The page freezes, buttons stop working, and users 
    will be stuck with no explanation of what happened.

* Risk 2: Missing Dropdown Error States
  - Plain English: The status selector dropdown on the admin dashboard changes 
    immediately when clicked, but it doesn't wait to see if the server actually 
    succeeded in updating the database.
  - What it means to users: If a database error occurs, the dropdown will show 
    the order is updated (e.g., "Completed"), but it actually failed on the 
    backend. This leads to administrative confusion where the admin panel 
    displays incorrect order statuses.

--------------------------------------------------------------------------------
5. EXPLANATION OF THE RECOMMENDATIONS
================================================================================
These are the suggested fixes to resolve the issues completely:

* Recommendation 1: Standardize Backend Error Payloads
  - How to fix: Make the Java/Spring Boot backend return errors as structured JSON 
    objects (e.g., {"error": "Order not found"}) instead of plain text. This 
    keeps the communication format consistent.

* Recommendation 2: Implement Safe JSON Helper in Frontend
  - How to fix: Write safety code on the frontend that checks if the server's 
    response is actually a JSON format before trying to parse it. If it isn't 
    JSON, it should fail gracefully rather than crashing.

* Recommendation 3: Add Dropdown Rollback Logic
  - How to fix: If the server update fails, revert the dropdown status back to 
    its original value in the database and display a clear popup modal saying 
    "Failed to update status."

* Recommendation 4: Automated Testing
  - How to fix: Create automated test scripts (using Cypress or Playwright) that 
    run these validation tests automatically every time the software is updated. 
    This prevents bugs from creeping back into the system in the future.
--------------------------------------------------------------------------------
6. OPTIONS FOR HANDLING THE TC-STS-032 FAILURE
--------------------------------------------------------------------------------
If you want to handle or resolve the failure of TC-STS-032, you have two primary 
options:

* Option A: Fix the Code (Recommended)
  - What to do: Update the frontend (AdminPanel.jsx) to safely handle plain text 
    responses and backend errors without crashing, and configure the backend to 
    return JSON-formatted errors.
  - Pros: This fixes the actual security/stability issue, ensuring the dashboard 
    never crashes if an order is missing or database connectivity is lost.
  - Cons: Requires code changes in the frontend and backend.

* Option B: Replace the Test Case
  - What to do: Remove TC-STS-032 (non-existent order rejection check) from the 
    documents and replace it with a frontend feature check, such as "Dynamic 
    Stat Counter Updates" (verifying that updating an order's status properly 
    updates the summary count of Pending, Preparing, and Completed orders at 
    the top).
  - Pros: Enables reporting a 100% Pass Rate immediately without writing or 
    changing any application code.
  - Cons: Removes verification of error handling on the API level.
